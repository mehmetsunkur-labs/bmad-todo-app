### F1 — A delete queued behind a failed write comes back as that write's failure (2.2/2.4 ↔ 2.3) · **fix now (decided: acknowledge the delete)**
- **What happens:** when an edit's PATCH fails with a DELETE queued behind it, the "deleted" row returns in edit mode with "Couldn't save your edit…". This happens after "Todo deleted" was already announced, and focus is not restored.
- **Pinned by:** `todo-edit.test.tsx` "edit then delete: … a failed PATCH drops it with one edit toast". It asserts `rows()` still contains "Changed" and that `fieldIn(middle)` is reopened.
- **Other variants:**
  - Delete behind a failing **create**: `showCreateFailure` puts the deleted text back in the Add box as "Your text is back in the box" (`create-failure.ts`).
  - Delete behind a PATCH **404**: an edit gets the persistent Retry toast for a Todo the user deleted (`edit-failure.ts` 404 branch). No test covers this.
  - Delete behind a toggle: see the Accepted section.
- **Where it comes from:** `onError` clears all `pending(id)` and never tells the handler what was dropped (`todo-sync.ts:286-301`). The dropped delete's `movedFocus` entry is left behind (`delete-failure.ts:28`, written at `todo-list.tsx:236`).
- **Assessment:** this is the FR-10 protocol ("queued actions after it are dropped, one toast") applied literally. No single story could see the result, a deleted Todo resurrected under another action's copy.
- **Sources:** adversarial #1, verification-gap #1 and #2, edge-case #1.

### F2 — The inline edit field has no visible focus ring (2.4) · **fix now**
- **Code:** `edit-field.tsx:121` adds `focus-visible:ring-0 border-0 border-b` on top of `textarea.tsx`'s `outline-none`, which overrides the global `:focus-visible { outline-2 outline-offset-2 outline-ring }` (`index.css:182-184`).
- **Browser (dev stack):** a keyboard-opened field shows `outline: none`, a transparent ring and only a 1 px bottom border in the ring colour. The Edit button next to it shows `solid 2px`.
- **Rules broken:** DESIGN.md `focus-ring`, EXPERIENCE.md:148 ("the focus ring is always visible") and UX-DR15. None of the specs recorded it.

### F3 — Focus is lost to `<body>` when a PATCH 404 removes the focused row (2.2, 2.4) · **fix now (tracked nowhere)**
- **What happens:** the toggle and edit 404 paths remove the row with no focus handling. EXPERIENCE.md:148 says "Focus is never lost to `<body>` after any action".
- **Where it's recorded:** only in `deferred-work.md:4` and in spec-2-4's `deferred:`. The Never lists of 2.3 and 2.4 excluded it, and no story or sprint action item owns it.
- **Related gaps:**
  - The create-fails-with-a-queued-toggle removal doesn't assert focus (`todo-row.test.tsx:313`).
  - A reopened field doesn't take focus when focus was on the `tabIndex=-1` list region, where a click on blank list space puts it. `edit-failure.ts:66-67` and `delete-failure.ts:45-46` treat only `<body>` as free.
- **Sources:** spec reconciliation, edge-case #3.

### F8 — Smaller cross-story defects · **defer (low)**
- **Unbounded mutation cache:** mutations never leave it (`query-client.ts:24` `gcTime: Infinity`, pinned by AD-6). Each toggle, edit or delete adds one, and `confirmed`/`generation` are never pruned after a delete (adversarial #4, edge-case #6).
- **`schema: null` accepts any 2xx:** it resolves `null` for any 2xx with any body (`http.ts:109`), so a proxy's `200 text/html` would count as a successful DELETE. The contract is exactly `204` (adversarial #5).
- **Stale edit Retry toast:** it survives a local delete of that Todo, and Retry then 404s (adversarial #9). An edit failure after a local delete reopens a field that is pruned at once, which loses the attempted text (edge-case #2 and #5).
- **Two focus layout effects:** delete restore and edit autoFocus have no arbitration when failures overlap in one commit (adversarial #7).
- **Deleting while editing that row:** the field's blur saves (PATCH) before the DELETE queues (adversarial #3).
- **Blur-on-removal double PATCH:** after a 404 removes the focused edit row, a blur on removal can send a doomed PATCH through the stale `openEdit.current` (adversarial #2, edge-case #4). Maybe-false: it depends on the engine firing blur on removal, and the trigger (a toggle 404 while that row's field has focus) needs the field refocused after the toggle was clicked.
