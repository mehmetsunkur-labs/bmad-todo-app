### F1 — A failed create restored to the input is resubmitted under a new id, which defeats idempotency (1.3↔1.4 boundary) · **fix now**
- **Source:** `apps/web/src/features/todos/create-failure.ts:69-76`, where the input-empty branch restores `vars.description` and drops `vars.id`. Then `apps/web/src/features/todos/add-row.tsx:87`, where every submit calls `createTodo({ id: uuidv7(), … })`.
- **Why it matters:** the spine says idempotent ids exist to prevent "duplicates created by retries or races" (`ARCHITECTURE-SPINE.md:89`). Suppose a POST commits on the server but the client sees a 10 s timeout or a dropped response. The row rolls back and the text comes back. The user presses Enter, and the server now stores two Todos, both visible after reload.
- **How it was found:** all three lenses flagged it independently (adversarial #1, edge-case #1, verification-gap #2). No story triage covered it: 1.3 built replay, and 1.4 used it only on the busy-input Retry path.
- **Test gap:** `add-row.test.tsx:400-437` stops after checking the restored text and never resubmits.
- **Upstream lesson:** the epic spec says "Retry reuses the original id and payload" (`epics.md:108`), but says nothing about the restore path, which is effectively a user-driven retry.

### F2 — No test runs real server responses through the real client parser (1.3↔1.4) · **fix now** (user focus area)
- **Source:**
  - API tests compare literal bodies (`apps/api/test/todos.test.ts:113-156, 226-234`) and never import `ErrorEnvelopeSchema`.
  - Web tests stub `fetch` with hand-written envelopes (`apps/web/src/api/http.test.ts:8-12`, `add-row.test.tsx:397, 598-634`). The 409 on a fresh uuidv7 is a response the real server cannot produce.
  - `e2e/` is an empty package, `test:e2e` is a stub (`package.json:13`), and there is no CI config.
- **Consequence:** runtime drift is invisible to both green suites. Examples are a change in which stage emits `details`, or a reason string outside the enum. Compile-time drift is caught by the shared TypeScript types.
- **Upstream lesson:** AD-5 requires "each mapping has an API test", but nothing requires the client to parse those same bodies.

### F3 — `todo-sync` is not yet ready for Epic 2's write kinds (1.2↔1.4 → Epic 2) · **defer into Story 2.1/2.2 spec**
- **Source:**
  - `onError` always re-renders from the existing `confirmed` (`apps/web/src/api/todo-sync.ts:219-221`), and `onFailure` gets no access to sync state. The spine requires a PATCH 404 to set `confirmed = null` (`ARCHITECTURE-SPINE.md:94`).
  - A 204 resolves as `undefined as T` (`apps/web/src/api/http.ts:89/119`), not `null`, so a delete would store `undefined` in `confirmed`.
  - A list refetch writes the raw server list and ignores pending ops (`apps/web/src/api/hooks/use-todos-query.ts:20-24`). `seedFromList` also nulls confirmed ids missing from a stale list (`todo-sync.ts:47-56`).
  - `kind` is an untyped string that is never read (`todo-sync.ts:16,174`).
- **Current risk:** latent. `resetQueries` is reachable only from Load error, where the Add row is disabled. I verified this: the only `resetQueries` call is at `use-todos-query.ts:31`.

### F4 — Create replay semantics will misfire once edit and delete exist (1.3 → Epic 2) · **defer into Story 2.1 spec**
- **Source:** `apps/api/src/services/todo-service.ts:64-77`.
  - A replay compares against the *current* Description, so a late create retry after an edit returns 409, and the client rolls back a Todo that exists.
  - The "row vanished" branch re-inserts, so a stale create retry after a delete brings the Todo back.
- **Found by:** adversarial #8 and #9.

## Behavior verification

Exercised end to end against the running dev stack (`web` on :18080 through the Vite proxy, `api`, `db`) on 2026-09-25. Probe rows were deleted from the dev DB afterwards.

**API via proxy (curl):**
- **Create:** a fresh POST returns 201 with a normalized Description (`"  retro\nprobe  "` → `"retro probe"`).
- **Replay and conflict:** a same-text replay returns 200 with the stored row; a different text on the same id returns 409 `CONFLICT`.
- **Validation (400):**
  - `empty`, `too_long` at 501 chars and at 251 emoji (502 UTF-16 units), `unknown_field`, and `invalid` id each return the correct detail.
  - Malformed JSON and an empty JSON body each return a 400 envelope.
- **Other status codes:** 413 for over 16 KiB, 415 for text/plain and for no content type, and 404 envelopes for an unknown route and for DELETE on the collection.
- **Resilience:** health returned 200 after all the abuse, and the API log shows one JSON line per request with no body.

**Browser (Playwright 1.x headless Chromium, scratchpad script):**
- **Populated load:** title and h1 are "Todos". Rows are newest first. `<b>…</b>` renders literally, with no links. The input is auto-focused. No console errors.
- **Add:**
  - Whitespace submit sends 0 POSTs.
  - The optimistic row appears at the top in about 28 ms, the input clears and keeps focus, and "Todo added" is announced.
  - The row is still at the top after reload.
- **Counter:** hidden at 449, "450 / 500" at 450; `maxlength` clamps input at 500.
- **Create failure, empty input:**
  - Network abort, 500 envelope, 502 HTML, 409 and 201 with the wrong shape each roll the row back, restore the text, keep focus, and show one toast: "Couldn't add that todo. Your text is back in the box."
  - A 400 `too_long` shows the too-long copy.
- **Create failure, busy input:** the typed text is kept and one persistent toast appears ("Couldn't add “…”." with Retry). Retry re-adds the row, and the toast clears.
- **List states:**
  - Empty: "Nothing here yet." / "Add your first todo above."
  - Load error: `role="alert"` and the Add row is disabled. Try again recovers to Populated.
  - Loading: no skeleton at 150 ms, then 4 skeletons with `aria-busy="true"` at 550 ms.
- **320 px with 1,000 Todos (stubbed GET):** no horizontal scroll, and the input and button are 44 px tall. Full navigation through the last row attached took **2030 ms**. That is against Vite dev mode (unbundled modules), so it is borderline against NFR "interactive within 2 s" but not a production measurement. Re-measure on the production-like stack in Story 3.4.
- **Dark mode with reduced motion:** body is `oklch(0.145 0 0)` and the primary button is `#5FB3AA`.

**Suites:** `pnpm -r test` gave 230 passed, 0 failed, 0 skipped (shared 25, API 107, web 98). `pnpm lint` and `pnpm typecheck` exited 0.
